## 0. 一句话结论

- **K230**：`IMAGE_LOG_ENABLE = True` 时，每 `IMAGE_LOG_EVERY` 帧把**送进 AI 的那张图（旋转前，1280×720 每隔 4 个像素取 1 个 = 320×180）**
  存成 JPEG；每帧写一行 `frames.csv`（K230 时钟、**全部检测框（含爪子脚）**、跟踪器状态、本帧实际发出去的 X/Y/D 或心跳）；
  收到树莓派的 `SYNC <序号> <树莓派时间>` 记到 `sync.csv`。SD 卡快满时自动停存图，再满连 CSV 也停，**检测和发帧都不受影响**。**默认关闭**。
- **树莓派**：`config.K230_SYNC_PORT`（默认 `None` = 不发，已加入 `CALIB_KEYS`）。配了以后 `--record` 每秒、以及每条动作命令前后各发一条
  `SYNC`，序号记进 jsonl（`sync` 事件；`cmd` 事件多一个 `"sync": [前, 后]`）。没配时 jsonl 内容和原来**完全一样**。
- **对齐**：`research/align_k230_log.py` 按（序号, 时间原文）配对、加权线性拟合偏移 + 漂移、去离群点，输出 `dataset.csv`。
  合成数据（偏移 −4321.5s、漂移 60ppm、K230 每帧只查 3 次串口、3 条坏数据）上，**每张图的树莓派时间最大误差 0.5ms**。
- **帧格式、坐标约定、串口号、波特率、`IGNORE_REGIONS` 默认值都没改**。三套测试全部通过（第 6 节）；仿真成功率和改之前完全一样。

## 1. 接线（要用户来接、来确认）

```
 树莓派 4                                          K230（庐山派）
 ┌──────────────────────┐                        ┌─────────────────────────────┐
 │ 物理脚 29  GPIO5  RXD3 │◄──────── 原有 ─────────┤ IO3  UART1_TXD  （10 字节帧）  │
 │ 物理脚  7  GPIO4  TXD3 ├──────── 新增 ────────►│ IO4  UART1_RXD  （SYNC 标记）  │
 │ 物理脚 30  GND        ├──────── 原有 ─────────┤ GND                          │
 └──────────────────────┘                        └─────────────────────────────┘
       /dev/ttyAMA3  115200 8N1（dtoverlay=uart3）        UART1 115200 8N1
```

- **K230 端用同一个 UART1 的 RX，不另开串口**：`k230_sdcard/main.py` 一开头就已经把 FPIOA 4 号脚设成了 `UART1_RXD`
  （`fpioa.set_function(4, FPIOA.UART1_RXD)`，旁边原来就写着"⚠️ 请确认引脚"），而且收发波特率本来就一样（115200）。
  这样 K230 程序**不用改任何 UART / FPIOA 配置**，树莓派那边也只是用 `/dev/ttyAMA3` 的发送方向。
- **要用户确认的地方**：
  1. **庐山派排针上哪一个是 IO4**（看板子丝印 / 原理图；IO3 就是现在接树莓派 GPIO5 的那根，IO4 通常挨着它）。
     接之前确认 IO4 在板子上没有接按键、LED 之类的东西。
  2. 树莓派 GPIO4 确实是 TXD3：`pinctrl get 4`（老系统 `raspi-gpio get 4`）应显示 `TXD3` / `a4`。`dtoverlay=uart3` 开了就是。
  3. 两边都是 3.3V 电平，直接连，不要经过 5V 的东西。GND 已经共地，不用再接。
- `docs/论文研究方案.md` 第 6 节原来写的是 GPIO14（UART0），已按任务 11 报告的建议改成 GPIO4（不用动串口控制台 / 蓝牙）。

## 2. K230 端（`k230_sdcard/main.py`）

### 2.1 配置（开头"存图 + 同步标记"一节）

| 配置 | 默认 | 作用 |
|---|---|---|
| `IMAGE_LOG_ENABLE` | `False` | 总开关。`False` 时主循环和原来完全一样：不读串口、不碰 SD 卡、Profiler 不多一项 |
| `IMAGE_LOG_ROOT` | `/sdcard/datalog` | 根目录；每次运行新建一个会话目录 `s0001`、`s0002` … |
| `IMAGE_LOG_EVERY` | `1` | 每几帧存一张图（`frames.csv` 每帧都写） |
| `IMAGE_LOG_STEP` | `4` | 缩小倍数：1280×720 → 320×180 |
| `IMAGE_LOG_FORMAT` | `"jpg"` | JPEG；板子上所有 JPEG 接口都不可用时自动退回 `"rgb"`（原始平面 RGB） |
| `IMAGE_LOG_QUALITY` | `80` | JPEG 质量 |
| `IMAGE_LOG_SOURCE` | `"ai"` | `"ai"` = 就是送进 AI 的那张图（软件缩小）；`"chn1"` = 摄像头第 1 通道 ISP 硬件缩小（同一个传感器帧，不占 CPU，配置失败自动退回 `"ai"`） |
| `IMAGE_LOG_MIN_FREE_MB` | `200` | 剩余空间低于它停止存图（CSV 照写） |
| `IMAGE_LOG_STOP_ALL_MB` | `20` | 低于它连 CSV 也停 |
| `IMAGE_LOG_SPACE_EVERY` | `100` | 每存这么多张实测一次剩余空间，中间按已写字节估算（`statvfs` 在 FAT 上可能慢，不每帧调） |
| `IMAGE_LOG_BUDGET_MS` | `0` | >0：存图平均耗时（摊到每帧）超过它就自动改成隔更多帧存一张，保帧率 |
| `IMAGE_LOG_FLUSH_EVERY` | `10` | `frames.csv` 每几行 flush（断电最多丢这么多行） |
| `SYNC_RX_ENABLE` | `True` | 存图打开时是否接收同步标记 |

### 2.2 主循环里插在哪（全部在 `if dlog is not None:` 后面）

| 位置 | 做什么 |
|---|---|
| `sensor.snapshot` 之后 | `frame_begin`：记**拍照时刻**（K230 微秒时钟），收一次同步标记；`chn1` 模式下再取一张第 1 通道的图 |
| `kpu.run()` 之后 | 再收一次同步标记（KPU 最耗时，中间多查一次，同步时刻更准） |
| 后处理之后、忽略区域过滤之前 | 复制一份**全部检测框**（爪子脚也记下来，标 `ign=1`；论文 H2 要用） |
| `send_position_via_uart` 里 | 通过 `_send_hook` 记下本帧实际发出去的 X/Y/D（取整后的、和线上字节一致）和发送时刻 |
| 显示之后、`del np_img` 之前 | `frame_end`：再收一次同步、存图、写 `frames.csv`。**放在发帧之后**，存图再慢也不会推迟本帧的串口发送 |

同步串口用 `uart.any()` + `uart.read(n)` 读，**不阻塞**（UART 设置了 `timeout=1000`，所以一定先看 `any()`；没有 `any()` 的固件就不收）。
每次读到一整行，记下 `(上一次查串口的时刻, 这一次的时刻]`：同步行的最后一个字节就是在这个区间里到的，离线对齐取中点、区间半宽就是这一条的不确定度。
一帧查 3 次（约 140ms 一帧），区间半宽大约 20~30ms，几千条一平均，偏移误差就降到 1ms 以内（见 6.3）。

K230 时钟：`time.ticks_us()` 约 18 分钟回绕一次，`MonoUs` 每帧累加 `ticks_diff`，得到不回绕的微秒数，CSV 里写成毫秒（1 位小数）。

### 2.3 JPEG 怎么编（⚠️ 板子上要确认）

CanMV 的图像接口版本差异大，云端没法确认，所以程序**第一张图时按顺序试，第一个成功的固定下来**，终端打印 `[DATALOG] 存图方式: xxx`：

1. （仅 `chn1`）第 1 通道图像 `.to_jpeg()` / `.compress()`，再 `.save()`
2. 把 `np_img[:, ::4, ::4]` 拷成 (3,180,320) 数组 → `image.Image(320, 180, image.RGBP888, data=...)` → `.to_rgb888()` → `.to_jpeg()` / `.compress()`
3. 同上但不 `to_rgb888`
4. 同 2 但用 `.save(path, quality=)`
5. **退路**：直接写原始平面 RGB（`.rgb`，3×320×180 = 168.75KB/张），电脑上 `python3 k230_sdcard/tools/raw2png.py <会话目录>` 转 PNG

JPEG 结果必须以 `FF D8` 开头才算成功（按 `size()` 截断，不会把整块缓冲区写进去）。选定后连续 5 次失败就停存图（CSV 照写）。
**如果板子上打印的是 `raw`**，说明 2~4 都不行，请把终端里 `编码方式 xxx 不可用: ...` 的报错贴回来，我按实际接口改；
同时可以试 `IMAGE_LOG_SOURCE = "chn1"`（CanMV 例程里第 1 通道 RGB888/RGB565 的图一般能直接 `compress`）。

### 2.4 帧率影响（目标：下降 ≤ 20%；**真机由用户测**）

存图开着时 Profiler 多一项 `datalog`。下降比例 = `datalog / total`；要 ≤ 20%，就要 `datalog ≤ 0.25 × 原来的 total`，
按现在约 7 帧/秒（`total` ≈ 140ms）算，**存图摊到每帧要 ≤ 35ms**。

估算（未实测，按 K230 大核 1.6GHz、SD 卡顺序写 10MB/s 量级推的）：

| 项 | 每次 | 说明 |
|---|---|---|
| 查同步串口 ×3 | < 0.1ms | `uart.any()`，没数据直接返回 |
| `frames.csv` 一行 | 0.3~1ms | 约 100~200 字节字符串格式化 + 写入，每 10 行 flush |
| 缩小拷贝 | 2~5ms | `np_img[:, ::4, ::4]` → 172KB |
| JPEG 编码 320×180 | 5~15ms | 软件编码；`chn1` 模式省掉缩小拷贝 |
| 写 JPEG（10~20KB） | 2~5ms | |
| **合计（JPEG，每帧存）** | **约 10~25ms** | **≈ 7%~15%**，在目标内 |
| 退路 `raw`（172KB/张） | 20~40ms | ≈ 15%~22%，超了就设 `IMAGE_LOG_EVERY = 2` 或 `IMAGE_LOG_BUDGET_MS = 30` |

## 3. SD 卡目录结构和字段

```
/sdcard/datalog/
  s0001/                    每次运行程序一个会话（K230 没有可靠的日期时间，用序号）
    info.txt                本次参数：img_w/img_h/step/every/format/quality/source/rotate_deg/labels/时钟说明
    frames.csv              每帧一行
    sync.csv                每个同步标记一行
    img/0000/000000.jpg     图像；每 1000 帧一个子目录
    img/0000/000001.jpg
    img/0001/001000.jpg
  s0002/ ...
```

> 和任务说明的 `<会话>/<帧号>.jpg` 略有不同：**每 1000 帧分一个子目录**。FAT 单个目录里文件多了（10 小时 ≈ 25 万张），
> 每新建一个文件都要线性扫目录，越存越慢，而且 FAT32 单目录有 65535 个目录项上限。文件名还是帧号。

**frames.csv**

| 列 | 含义 |
|---|---|
| `frame` | 帧号（程序启动后从 0 起，和图像文件名一致） |
| `t_ms` | **拍照时刻**，K230 时钟（毫秒，不回绕，程序启动时约为 0） |
| `img` | 图像相对路径（这帧没存图则为空） |
| `n_det` | 检测框个数（忽略区域过滤之前） |
| `dets` | 全部检测框 `类别:置信度:x1:y1:x2:y2:ign`，用 `\|` 分隔；**原始 AI 画面像素（1280×720，旋转前）**；`ign=1` = 中心在忽略区域里（爪子脚） |
| `trk` | 跟踪器状态：`none` 没目标 / `tent` 刚出现未确认 / `lock` 锁定 / `hold` 锁定但本帧没检测到（预测中） |
| `trk_cls` `trk_score` `trk_box` | 跟踪器的类别、平滑后的置信度、平滑后的框 `x1:y1:x2:y2`（原始像素） |
| `sent` | 本帧发出去的帧：`pos` 位置帧 / `hb` 心跳 / 空 = 没发 |
| `sx` `sy` `sd` | 发出去的 X/Y/D（和线上字节一致，mm，已按 `POSITION_IN_ROTATED_FRAME` 旋转） |
| `t_send_ms` | 发送时刻（K230 时钟） |

图像本身是**旋转前**的（和 `dets` 坐标一致）；要看成 IDE 里的方向，按 `info.txt` 的 `rotate_deg` 顺时针转 90°。

**sync.csv**：`seq`（序号）、`pi_t`（树莓派时间原文，秒，4 位小数）、`k230_ms_prev` / `k230_ms`（收到这一行的区间，K230 时钟）、`frame`（当时的帧号）。

## 4. 树莓派端

- `config.py`：`K230_SYNC_PORT = None`、`K230_SYNC_PERIOD_S = 1.0`，都在 `CALIB_KEYS`。真机在 `calib.json` 里加
  `"K230_SYNC_PORT": "/dev/ttyAMA3"`。和 `PORTS["k230"]` 相同时**复用 K230 已经打开的 serial 对象**（同一个 fd，读线程收、这里发），不会再开一次口；
  填别的串口则单独打开（波特率用 `BAUD["k230"]`）。
- `recorder.py`：新增 `SyncSender`（发 `SYNC <序号> <t>\n`，t 是树莓派单调时钟 = jsonl 里的 `t`，4 位小数）和 `open_sync_writer`。
  `Recorder(..., sync=None)`：
  - 每条记录的动作命令（`RecordProxy`）**前后各发一条**，`cmd` 事件里加 `"sync": [前序号, 后序号]`；
  - 读帧线程每次轮询时，距上次发送 ≥ `K230_SYNC_PERIOD_S` 就发一条（`why: "tick"`）；
  - 每条都记 `{"ev":"sync","t":发出时刻,"seq":…,"pi_t":"原文","why":"tick/pre/post"}`；写串口失败只记 `err`，不抛异常、不影响抓取。
- `main.py get_recorder`：配了 `K230_SYNC_PORT` 才创建 `SyncSender`，串口打不开就打印警告、照常记录不发同步。
- 只有 `--record`（或 `GRASP_RECORD=1`）时才会发；不记录时完全不碰这个口。

## 5. 离线对齐 `research/align_k230_log.py`

```bash
cd raspberrypi/grasp
python3 research/align_k230_log.py --record logs/record_*.jsonl --k230 /path/datalog/s0003 -o dataset.csv
#   --k230 可以给多个会话，每个 record 文件自动找配对最多的那个；--all-frames 连没存图的帧也输出
```

1. **配对**：按（序号, 时间原文）配对。树莓派程序重启后序号从 1 重来，但时间原文不会重复，所以不会配错（测试里专门放了一个序号相同、时间不同的假会话）。
2. **拟合**：`pi_t = a + b × k230_s`。K230 侧取区间中点；树莓派侧加上发送这一行的时间（字节数 × 10 / 115200 ≈ 2ms）。
   按 `1 / (区间半宽 + 1ms)²` 加权（卡顿的那一帧区间宽、不准），残差超过 `max(4 × 1.4826 × MAD, 半宽 + 2ms)` 的去掉再拟合，迭代 3 次。
   只配上 1 条时只估偏移（漂移按 0）并警告。
3. **数据集**：每张图的 `t_ms` 换算成树莓派时间，查 jsonl：

| 列 | 含义 |
|---|---|
| `record` `session` | 来自哪个树莓派记录文件、哪个 K230 会话 |
| `image` `frame` `k230_ms` `pi_t` | 图像路径、帧号、K230 拍照时刻、换算后的树莓派时间（秒，和 jsonl 的 `t` 同一个时钟） |
| `episode` `result` | 第几次抓取、这次的结果（`episode_start` 到 `episode` 之间的图才有） |
| `phase` | 当时任务打印的最后一行（`say`，截 40 字，用来切分对准 / 抓取 / 确认阶段） |
| `in_cmd` | 拍照时是否正在执行某条命令（命令的 `t ≤ pi_t ≤ t_end`） |
| `prev_cmd` `prev_cmd_t` `prev_cmd_args` `dt_prev_end` | 之前最近一条命令（`设备.函数`、开始时间、参数 JSON、拍照时刻减去它的结束时间） |
| `next_cmd` `next_cmd_t` `next_cmd_args` | 之后最近一条命令 |
| `s1`…`s6` | 机械臂各舵机**命令**脉宽（最近一条已发出的机械臂命令之后的状态；舵机实际到没到位不知道——这正是论文要学的） |
| `lift_cm` `lift_busy` | 升降轴高度（最近一条已结束的升降轴命令之后的 `pos`）、是否正在动（`move_*` 期间或 `start_move_by` 到 `wait_move` 结束之间） |
| `sent` `sx` `sy` `sd` `trk` `n_det` | 照抄 `frames.csv`：本帧发出去的帧、跟踪器状态、检测框数 |

4. **自检**（报告里自动打印）：K230 发出的每个位置帧（`frames.csv` 有发送时刻和 X/Y/D），在树莓派 jsonl 里应该有一条
   X/Y/D 完全相同的 `k230` 事件（树莓派接收时刻）。用拟合的时钟预测接收时刻，和实际比：残差 = 串口传输约 1ms + 树莓派读线程等待
   （`devices.K230` 用 `ser.read(64)`、`timeout=0.05`，最多等 50ms）+ **对齐误差**。这是一个和同步标记完全独立的检验。

### 6.2 树莓派同步标记（4 节，12 项）

### 6.3 时钟对齐（5 节，11 项，合成 20 分钟数据）
合成：K230 时钟 = (树莓派 − 4321.5s) × (1 + 60ppm)；每帧 140±20ms、1% 的帧卡 +400ms；每帧在 0 / 45% / 85% 处查串口；
每秒 + 每条命令前后发同步（共 2395 条）；故意弄坏 3 条（K230 时刻 +500ms）；每两帧发一个位置帧，树莓派接收 = 发送 + 0.9ms + U(0, 50ms)。


## 7. 真机验证步骤

**A. 接线和同步链路（不开存图也能测）**
1. 按第 1 节接线（先确认 IO4）。树莓派 `pinctrl get 4` 显示 TXD3。
2. K230 程序里设 `IMAGE_LOG_ENABLE = True`，在 IDE 里运行；终端应打印 `[DATALOG] 记录到 /sdcard/datalog/s000N ... 同步接收 开`
   和 `[DATALOG] 存图方式: xxx（nnnn 字节/张）`。**记下是哪种方式**；如果是 `raw`，把前面几行"不可用"的报错贴回来。
3. 树莓派上（K230 程序运行时，抓取程序没在跑）：先 `stty -F /dev/ttyAMA3 115200 raw -echo`（没有程序打开过时波特率可能不是 115200），
   再 `printf 'SYNC 1 123.4567\n' > /dev/ttyAMA3`。停掉 K230 程序后看 `sync.csv` 有这一行
   （程序每 300 帧也会打印 `[DATALOG] 图 … | 同步 n 个`）。

**B. 帧率（目标下降 ≤ 20%）**
1. `IMAGE_LOG_ENABLE = False` 跑 1 分钟，记下终端 `[timing ms/frame] ... total XXX (YY fps)` 和 OSD 上的 FPS。
2. `IMAGE_LOG_ENABLE = True` 再跑 1 分钟，看同一行里新增的 `datalog` 项和 total。**下降 = datalog / total**。
3. 超过 20%：先试 `IMAGE_LOG_SOURCE = "chn1"`；还不行设 `IMAGE_LOG_EVERY = 2` 或 `IMAGE_LOG_BUDGET_MS = 30`。
4. 顺便看 `datalog` 项稳不稳：偶尔一帧特别长（SD 卡写入卡顿）没关系，CSV 和图像不影响串口发送的时机（存图在发帧之后）。

**C. 对齐误差**
1. `calib.json` 加 `"K230_SYNC_PORT": "/dev/ttyAMA3"`，`python3 main.py --once --no-chassis --record` 跑几次抓取；`recorder.py summary` 应能看到 `sync=…`。
2. 把 SD 卡的 `datalog/s000N/` 和树莓派的 `logs/record_*.jsonl` 拷到同一台电脑，跑 `align_k230_log.py`，把它打印的三行贴回来：
   - 配上的数量 ≈ 树莓派发的数量（少很多 = 丢字节 / 波特率不对 / 接错脚）
   - **漂移**：两颗晶振一般在 ±100ppm 内；**残差 RMS** 应 ≈ 区间半宽 / √3（每帧 140ms、查 3 次时约 15~25ms），远大于这个说明 K230 时钟或采样有问题
   - **自检**：对上比例应接近 100%；中位数应在 0~50ms 之间（树莓派读线程的等待），95% 分位 ≤ 55ms 左右。
     如果中位数是负的或 > 60ms，说明对齐有系统偏差
3. 直观检查：在 `dataset.csv` 里找一次底座转动（`prev_cmd = arm.move`、`in_cmd` 由 0 变 1），对照前后几张图，物块应该在命令开始之后（加上舵机反应时间）才开始移动。

## 8. 没做 / 风险

- **CanMV 接口未确认**：`image.Image(..., RGBP888, data=ndarray)`、`to_rgb888`、`to_jpeg` / `compress`、`PIXEL_FORMAT_RGB_888`（chn1）、
  `os.statvfs` 在你的固件上的实际名字和行为。都包了 try，最坏情况是退回 `raw` 或者不记录，**不会影响检测和发帧**；但 `raw` 体积大约是 JPEG 的 10 倍。
- `chn1` 那张图和 AI 那张图**可能不是同一个传感器帧**（两次 snapshot 先后取），差最多一帧；要严格同一帧用默认的 `"ai"`。
- 只开了树莓派同步、K230 没开存图时，K230 的 UART1 收到的字节没人读，会被驱动丢掉，**不影响**发帧（发和收是两个方向）。
- 每帧只在 3 个时刻查串口，单条同步的不确定度约 ±20~30ms，靠数量平均；如果真机漂移不是常数（温度变化大），可以以后改成分段拟合。
- 数据集里机械臂是**命令**脉宽，不是实际角度（没有反馈）；舵机电位器真值是研究方案 3.5 的另一件事。
- 树莓派那边 `k230` 事件的接收时刻本身有 0~50ms 的读串口等待（`devices.K230` 的 `timeout=0.05`）；这次没改（任务要求不动现有驱动行为），
  数据集里的图像时间不受它影响（用的是同步标记），只影响自检残差的大小。
